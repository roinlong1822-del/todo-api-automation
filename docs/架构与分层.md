## 1. 整体架构

```
┌──────────────────────────────────────────────────────────────┐
│  测试开发者(你)                                              │
└───────────────┬──────────────────────────────────────────────┘
                │ 1. 按契约设计用例
                ▼
┌──────────────────────────────────────────────────────────────┐
│  api_test/  测试框架(项目 B · 简历主体)                     │
│                                                              │
│  testcases/  用例层:写断言(表达业务预期)                    │
│      │       只能调 api/ 与 utils/,不出现 URL/裸路径         │
│      ▼                                                       │
│  api/        业务接口层:一个接口一个方法                     │
│      │       create_todo(title) / list_todos(page, size) …    │
│      ▼                                                       │
│  utils/      通用能力层:HttpClient / logger / asserts / db    │
└───────────────┬──────────────────────────────────────────────┘
                │ 2. HTTP(JSON over HTTP)
                ▼
┌──────────────────────────────────────────────────────────────┐
│  api_server/  被测系统(项目 A)                              │
│  FastAPI 路由 → 业务规则 → SQLAlchemy → SQLite               │
│  特性:OpenAPI /docs、种子数据、故障注入开关                   │
└──────────────────────────────────────────────────────────────┘
```

**关键点**:两个项目**互不 import**,只通过 HTTP 交互 —— 这样才能真实模拟"测别人的服务"。

## 2. `api_test/` 分层与依赖方向

```
testcases/          用例层  ── 可以 import →  api/, utils/, data/
   │
   ├──> api/        业务接口层 ── 可以 import →  utils/
   │       │
   └──> utils/      通用能力层 ── 不 import 上层(最底层)
   
config/   横切:环境配置(被各处读取)
data/     横切:测试数据与常量
conftest.py  pytest 共享 fixture(客户端、鉴权态、DB 会话、数据清理)
```

### 每层的"能与不能"

| 层 | 能做什么 | 不能做什么 |
|---|---|---|
| `testcases/` | 调 `api.xxx()`、写断言、组织用例 | ❌ 拼 URL ❌ 直接用 `requests` ❌ 写超时字面量 |
| `api/` | 把 HTTP 细节翻译成业务语义、返回 `Response` | ❌ 写断言 ❌ 决定对错 |
| `utils/` | 提供通用能力(客户端、日志、断言工具、DB) | ❌ 写业务语义 ❌ 写断言 |
| `api_server/` | 实现契约、维护数据一致性 | ❌ 感知测试代码存在(除了故障注入开关) |

## 3. 一次请求的完整数据流

```
用例: assert todo_api.create_todo("买牛奶").status_code == 201
   │
   ▼  api/todo_api.py   组装 json={"title": "买牛奶"}  →  client.post("/todos", json=…)
   ▼  utils/http_client.py  拼 base_url + 超时兜底 + 打请求日志 + 返回 Response
   ▼  HTTP POST /todos  ────────────────►  api_server
                                          routers/todos.py 校验参数
                                          models 写库(SQLAlchemy commit)
                                          返回 201 + body
   ◄──────────────────────────────────────
用例: 断言状态码;必要时再查库做【双端校验】
```

## 4. 关键设计决策(面试会问)

| 决策 | 选择 | 理由 |
|---|---|---|
| 为什么自建被测服务 | 而非测公开 API | 可控、能造异常、能注入故障、能做双端校验、第三方不稳定(踩过 502) |
| 客户端为什么封装 | `utils/http_client.py` | 环境/超时/日志/鉴权收在一处;用例不碰 HTTP 细节 |
| 为什么要有业务接口层 | `api/` | 接口变了只改一层;用例读起来像业务描述 |
| 断言放哪 | 只在 `testcases/` | 断言是业务预期,封装层写断言会让"测 404"的用例无法通过 |
| 数据隔离怎么保证 | fixture 作用域 + 事务回滚 + 唯一前缀 | 用例可重复运行、可并行 |
| 数据库为什么选 SQLite | 零安装、支持事务回滚、可移植 | 换 MySQL 只改 `DATABASE_URL`(会做一次切换验证) |
| 怎么证明测试有价值 | **故障注入** | "返回 201 但没落库"只有双端校验能抓到,可现场演示 |
| 怎么处理不稳定 | 本地 mock 优先 + 外网用例打 `network` 标记 + 重试只给已知不稳定用例 | 稳定性 > 覆盖率 |

## 5. 数据隔离策略(三层防线)

```
① 用例级:每条用例自己造数据(唯一前缀,如 title=f"t_{uuid4().hex[:8]}")
② 事务级:DB fixture 用事务包裹,teardown 回滚(不污染种子数据)
③ 环境级:CI 每次跑之前重建 SQLite 文件 + 重新 seed
```

**验收标准**:同一批用例连跑两次结果一致;打乱顺序结果一致;将来并行(`-n 4`)也一致。
