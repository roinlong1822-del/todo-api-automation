## 6. 三连问:环境变量 / 前缀判断 / sqlite 跨线程(附实测)

### 6.1 `os.getenv(key, default)` 是什么

从**环境变量**读配置;变量不存在时返回 `default`。它让**同一份代码**靠环境切换数据库、密钥、环境名 —— 不用改代码。

```python
DATABASE_URL = os.getenv("DATABASE_URL", "sqlite:///./api_server.db")
```

实测行为:

| 情况 | 结果 |
|---|---|
| 变量不存在、没给默认 | `None` |
| 变量不存在、给了默认 | `sqlite:///./api_server.db` |
| 设置了环境变量 | 环境变量的值(`mysql+pymysql://…`) |
| 返回值类型 | **永远是 `str` 或 `None`**(不会自动转 int/bool) |

⚠️ **常见坑**:`.env` 文件**不会自动生效**。本项目里是显式传环境变量:

```bash
APP_ENV=test python -m uvicorn api_server.app.main:app --port 8000
```

### 6.2 `DATABASE_URL.startswith("sqlite")` 在判断什么

判断的是 **`os.getenv` 的最终返回值**(有环境变量用环境变量,没有用默认值)。默认值 `sqlite:///./api_server.db` 以 `sqlite` 开头 → 条件为真。

为什么这么判断:`DATABASE_URL` 是 **URL**,`scheme://` 前面那段就是**方言标识** —— `sqlite` / `mysql+pymysql` / `postgresql`。不同方言需要不同的连接参数。

更稳的写法(不用手动切字符串):

```python
from sqlalchemy.engine import make_url
make_url(DATABASE_URL).get_backend_name()     # 'sqlite' / 'mysql' / 'postgresql'
```

**sqlite URL 里斜杠数量的含义**(写错会把文件建到别处):

| URL | 含义 |
|---|---|
| `sqlite:///./api_server.db` | 相对路径 `./api_server.db` |
| `sqlite:////tmp/abs.db` | 绝对路径 `/tmp/abs.db`(四个斜杠) |
| `sqlite:///:memory:` | 内存库(进程结束即消失) |

### 6.3 `connect_args={"check_same_thread": False}` 是什么意思

直译没错 —— **"检查同一线程"**,这是传给 Python `sqlite3` 的开关,**默认 `True`**。

含义:默认要求**连接只能在创建它的那个线程里使用**,跨线程用会抛异常。实测:

```
默认(True)跨线程使用    : ProgrammingError: SQLite objects created in a thread
                          can only be used in that same thread...
check_same_thread=False : OK
```

**为什么 Web 服务要关掉**:uvicorn/FastAPI 用**线程池**处理请求,连接可能被不同线程使用;不关就会在并发时炸(FastAPI 官方文档对 SQLite 的示例也是这么写的)。

**关掉安全吗**:等于"把检查关掉、责任交给你"。我们的用法是**每个请求一个 Session**(`get_db`),不共享连接做并发写。SQLite 本身并发写能力弱,只适合测试/小规模;换 MySQL 时这个参数不需要(代码里已用 `else {}` 处理)。

> 记忆:这是 **sqlite 驱动层**的限制,不是 SQLAlchemy 的,也不是 HTTP 的。

### 6.4 追根问底:`check_same_thread=False` 会"提高并发能力"吗?

**不会。** 这里有两个**不同层次**的限制,很容易混:

| | 限制 A:驱动层 | 限制 B:数据库引擎层 |
|---|---|---|
| 内容 | 同一个 `sqlite3.Connection` **对象**不能跨线程使用 | 写事务互斥:**整库写锁** |
| 谁管 | Python `sqlite3` 的 `check_same_thread` | SQLite 引擎(文件锁) |
| 能否关掉 | ✅ 能(`False`)——但它只是**移除一个检查**,不是能力开关 | ❌ 关不掉 |
| 实测现象 | 跨线程调 `execute/commit/rollback/close` → `ProgrammingError` | 两线程并发写 → `OperationalError: database is locked` |
| 本项目的处理 | 关掉(因为连接池会把连接交给不同线程) | 接受;真要高压并发就换 MySQL |

**为什么 FastAPI/连接池必须关掉 A**:SQLAlchemy 的 `QueuePool`(文件型 SQLite 的默认池)会把**同一个连接在不同时间交给不同线程**(借出 → 归还 → 再借出)。这个"**先后交接**"就会踩到 A 的检查。
SQLAlchemy 官方文档因此对**文件型 SQLite 默认就把 `check_same_thread` 设为 `False`**(见 `sqlalchemy/dialects/sqlite/pysqlite.py` 文档:"SQLAlchemy's default behavior here is to set `check_same_thread` to `False` automatically whenever a file-based database is in use, to establish compatibility with the default pool class QueuePool")。
→ 我们代码里那行 `connect_args={"check_same_thread": False}` 属于**显式写法**,默认已是 False(但写出来更清楚,也是 FastAPI 官方示例的写法)。

**关掉 A ≠ 提高并发**:实测两个线程**各自使用独立连接**并发写,依然被 B 挡住:

```
线程2: OperationalError: database is locked
```

**"同一时刻只有一个线程能用同一个连接"这条依然成立**,由架构保证:
① 每个请求一个 Session(`get_db`)② 连接池 checkout 是独占的 ③ 用完 `rollback` + 归还。

**两个相关事实**:
- `sqlite:///:memory:` 走 `SingletonThreadPool`(**每线程一条连接**)→ **不同线程看到的是不同的内存库**;要在多线程间共享内存库必须 `StaticPool` + `check_same_thread=False`
- `PRAGMA journal_mode=WAL` 可让"读不阻塞写",改善并发表现(默认是 `delete`)

> 实验设计教训:我第一次验证这个结论时**没控制好变量**(连接建在主线程、子线程只记录 ident),得到"跨线程使用被允许"的**假结论**;
> 改成"逐个操作、确定性触发"后才得到正确结果(所有操作都抛 `ProgrammingError`)。
> 这就是"控制变量"为什么重要 —— 实验设计错了,结论就是错的。

### 6.5 重要发现:这个检查**本身不可靠**(线程标识会被回收复用)

实验:A 线程创建连接后**退出**,B 线程再使用这条连接 —— 结果**被允许了**。原因:

```
线程A(创建连接者,已退出) ident : 134853227333312
线程B(后来者)            ident : 134853227333312     ← 完全一样!
两者相同?                       : True
线程B 使用 A 的连接              : ✅ 允许
```

CPython 文档原话(*threading.get_ident*):
> "Thread identifiers may be recycled when a thread exits and another thread is created."

**推论**:`check_same_thread` 是基于**线程标识**的比较,而标识会被回收 → 它既可能误拦(常见),也可能**漏放**(如本例)。所以它只是**"尽力而为的误用提示",不是并发安全机制**。

对照实验(让 A **保持存活**,标识必然不同):

| 场景 | 结果 |
|---|---|
| A 存活,B 用 A 的连接(`check_same_thread=True`) | ❌ `ProgrammingError` |
| 同上,但 `check_same_thread=False` | ✅ 允许 |
| 关掉检查后,两线程**同时**用同一连接 | ❌ `OperationalError: cannot start a transaction within a transaction` |

**正确的概念表述**(把这三句记住就够了):

| 说法 | 判定 |
|---|---|
| 同一连接**不能被两个线程同时使用** | ✅ 对,而且是**必须自己保证**的红线(没有检查帮你拦) |
| B 不能用 A 创建的连接,**即使 A 早就用完了** | ✅ 在 `True` 下成立 —— 因为这个检查**只看"谁创建的"**,不看"是否正在被占用" |
| 设 `check_same_thread=False` 可允许**跨线程先后使用** | ✅ 对;但动机是**连接池的交接**(借出→归还→再借出),而且 SQLAlchemy 对文件型 SQLite 默认已是 False |
| 关掉检查 = 提高并发能力 | ❌ 不成立;并发上限由 **SQLite 写锁**决定 |

> 元教训:为了验证"跨线程使用会被拦"这一条,我改了三次实验设计才复现成功 ——
> 前两次分别因为"连接建在主线程"和"线程标识被复用"而得到**假结论**。
> 实验设计错了,结论就是错的,而且它看起来很像真的。

## 7. 拆开 `SessionLocal = sessionmaker(bind=engine, autoflush=False, autocommit=False)`

### 7.1 一行五个部分

| 部分 | 是什么 | 说明 |
|---|---|---|
| `SessionLocal` | 变量名(约定:**大写 L** 表示它是"类/工厂",不是实例) | 调用它才得到一次会话 |
| `sessionmaker(...)` | **类工厂**:按配置生成一个绑定好的 `Session` 类 | 类比 C++ 的"工厂返回的类型" |
| `bind=engine` | 会话要用的**引擎**(= 连接池 + 方言) | 换 engine 就换数据库,代码不变 |
| `autoflush=False` | **查询前不自动刷写**待提交的改动 | 默认是 `True` |
| `autocommit=False` | 明确"不做自动提交" | 2.0 里语义已是默认;写 `True` 会报错 |

### 7.2 六个实验(实测)

**① 工厂 vs 实例**
```
SessionLocal         : sessionmaker(class_='Session', autocommit=False, bind=Engine(sqlite:///s1.db), autoflush=False, ...)
type(SessionLocal)   : sessionmaker      ← 它是「类」
type(SessionLocal()) : Session           ← 这才是一次数据库对话
```

**② `bind` 的作用**:同一份代码,绑不同 engine 就写不同库(实测 `a.db` / `b.db` 各自写入)。→ 这就是"换环境只改一处"的基础。

**③ `autoflush` 的区别**(add 之后立刻 query)
```
autoflush=True  → 看到 1 行(查询前自动 flush)
autoflush=False → 看到 0 行(不自动刷)
```
为什么设 False:避免"我还没想提交,SQL 却先发出去了"这种意外顺序,行为更可预测。

**④ `autocommit` 在 2.0 里已废弃**
```
sessionmaker(bind=e, autocommit=True)     # 不报错(它是惰性的,不立刻建 Session)
sessionmaker(bind=e, autocommit=True)()   # ❌ ArgumentError: autocommit=True is no longer supported
```
所以永远写 `autocommit=False`(或不写)。

**⑤ 会话隔离 —— 测试数据隔离的基础**
```
s1 flush 后,s1 自己看到 : 1 行
s1 flush 后,s2 看到     : 0 行   ← 别的会话看不见未提交数据
s1 commit 后,s2 看到    : 1 行
rollback 后未提交改动被丢弃
```
→ 一个 Session = **一个事务**;`flush` 发 SQL 但不提交,`commit` 才落库,`rollback` 全部撤销。

**⑥ 连接归还**:`session.close()` 之后连接回到池里
```
初始            : Connections in pool: 1  Checked out: 0
借出连接后      : Connections in pool: 0  Checked out: 1
session.close() : Connections in pool: 1  Checked out: 0
```

### 7.3 为什么用 `sessionmaker` 而不是直接 `Session(bind=engine)`

两者都能用。`sessionmaker` 的价值是:**配置只写一次,处处复用**(`SessionLocal()`),而且便于在测试里替换成别的 engine(比如指向测试库)。

### 7.4 本项目里的用法与红线

```python
def get_db():
    db = SessionLocal()      # 每个请求一个 Session
    try:
        yield db
    finally:
        db.close()           # 用完必须归还连接
```

| 红线 | 原因 |
|---|---|
| **一个请求/一条用例一个 Session** | Session 不是线程安全的,且它承载事务状态 |
| **写完必须 `commit`** | 否则接口返回 201 但库里没数据(和故障注入现象一样) |
| **用完必须 `close`** | 否则连接一直不被归还,池会被耗尽 |
| 不要在全局建一个 Session 反复用 | 事务/缓存会越滚越脏,且跨线程不安全 |

## 9. 配置加载与多环境切换(`config/loader.py`)

### 9.1 它要做的四件事

```
① 选环境: load_config("test") 的参数 > 环境变量 APP_ENV > 默认 "dev"
② 读文件: config/<env>.yaml(用 Path(__file__).parent 锚定,不依赖 cwd)
③ 解析  : yaml.safe_load(不是 load —— 安全)
④ 覆盖  : 环境变量优先级最高(CI/Docker 里不改文件就能换配置)
```

### 9.2 实现(可直接用)

```python
"""多环境配置加载:YAML + 环境变量覆盖。

优先级(从高到低):显式参数/环境变量  >  <env>.yaml  >  代码里的默认值
"""

import functools
import os
from pathlib import Path

import yaml

CONFIG_DIR = Path(__file__).parent          # ★ 锚定配置目录,不依赖当前工作目录


@functools.lru_cache(maxsize=None)
def load_config(env: str | None = None) -> dict:
    env = env or os.getenv("APP_ENV", "dev")
    path = CONFIG_DIR / f"{env}.yaml"
    if not path.exists():
        raise FileNotFoundError(f"配置文件不存在:{path}(可用 APP_ENV 指定 dev/test)")

    data = yaml.safe_load(path.read_text(encoding="utf-8")) or {}

    # 环境变量覆盖(CI/Docker 里最常用的手法)
    if v := os.getenv("API_BASE_URL"):
        data["base_url"] = v
    if v := os.getenv("HTTP_TIMEOUT"):
        data["timeout"] = float(v)

    data["env"] = env
    return data
```

### 9.3 在 `conftest.py` 里接入

```python
import pytest
from config.loader import load_config
from utils.http_client import HttpClient


@pytest.fixture(scope="session")
def config():
    return load_config()                     # 读一次,整个会话共用


@pytest.fixture(scope="session")
def server_api(config):                      # 不再硬编码地址!
    return HttpClient(config["base_url"], timeout=config["timeout"])
```

用法:默认用 `dev.yaml`;切环境只需 `APP_ENV=test pytest …`(或在 CI 里设 `API_BASE_URL`)。

### 9.4 两个坑(实测)

**① 环境变量覆盖是"全局"的,不分环境**
一旦 `export API_BASE_URL=...`,**任何 env 的 yaml 都会被它覆盖**。
→ 现象:"我明明改了 yaml,怎么没生效?" 解决:`unset API_BASE_URL`;测试里用 `monkeypatch` 隔离。

**② `lru_cache` 会盖住后续的环境变量变化**
```
设了 API_BASE_URL 后第一次调用 → http://127.0.0.1:9999
再改环境变量后调用(命中缓存) → http://127.0.0.1:9999   ← 旧值!
load_config.cache_clear() 后再调 → http://10.0.0.5:8080  ← 新值
```
→ 正常使用时环境变量在进程启动前就设好了,没问题;但**写测试改环境变量时记得 `load_config.cache_clear()`**。

### 9.5 练习(写完 loader 可以做)

1. 支持 `pytest --env=test` 命令行切换(用 `pytest_addoption` + 一个 fixture,把这个值传给 `load_config`)
2. 给配置加**校验**:缺 `base_url` 或缺 `timeout` 时报清晰错误(而不是后面某个奇怪的地方炸)
3. 支持**分文件**:`config/common.yaml` + `config/<env>.yaml`,后者覆盖前者(真实项目常见)
