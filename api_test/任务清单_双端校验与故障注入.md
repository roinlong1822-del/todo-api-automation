## 1. 先搞清概念:什么叫"双端校验"

| 端 | 怎么查 | 能发现什么 | 发现不了什么 |
|---|---|---|---|
| **接口端** | `r.status_code` / `r.json()` | 契约对不对、字段对不对、错误码对不对 | **接口撒谎**:返回成功但根本没写库 |
| **数据库端** | 直连 DB 查那一行(或通过第三方只读接口) | 数据真的落库了、软删除标记对不对、字段真值 | 数据"看起来对但业务规则错" |

**核心断言句式**:「接口说成功」**且**「库里真有这一行,且字段值与请求一致」。

### 实测:为什么单端不够

给写接口注入故障(`X-Inject-Bug: write_fail`)后,实测响应:

```
接口状态        : 201                                    ← 单端断言 r.status_code == 201 → 通过
响应体          : {"id": 0, "title": "这条不该落库", ...}
响应头          : X-Bug-Injected: write_fail
数据库里查这条  : None                                    ← 双端校验一查就露馅
```

注意 `id: 0` 是个**明显破绽**(真实自增 id 不可能为 0),所以"断言 `id > 0`"也能顺带抓到这一版注入。

**但更隐蔽的变种抓不到**:如果实现改成"返回一个真实的 id(比如借用了别的新增记录)但这一条没写库",单端断言全都通过。**只有双端校验能抓。**

## 2. 任务一 · `db` 夹具(约 20 分钟)

**改** `api_test/conftest.py`。需要新增:

```python
from api_server.app.database import SessionLocal, engine      # 顶部 import
from api_server.app.models import Todo                        # 只有在用例里要查表时才需要


@pytest.fixture(scope="session", autouse=True)
def _check_db_target():
    """防呆:sqlite 路径是相对 cwd 的,必须从仓库根运行 pytest。"""
    if engine.url.get_backend_name() == "sqlite":
        db_file = Path(engine.url.database).resolve()
        assert db_file.exists(), (
            f"数据库文件不存在: {db_file}\n"
            "双端校验必须在【仓库根】运行 pytest,否则会连到另一个空库。"
        )


@pytest.fixture
def db():
    """直连数据库的 Session:只用于**校验与清理**,不拿它造业务数据。"""
    session = SessionLocal()
    try:
        yield session
    finally:
        session.close()
```

**要点**
- `function` 作用域:每个用例一个干净 Session(用完就关,避免脏缓存跨用例)。
- **别用 `get_db()`**:它是生成器函数,是给 FastAPI 依赖注入用的(你在阶段 A 踩过这个坑)。
- 造业务数据仍然走接口(`todo_api.create_todo`),DB 只用来**验证**和**善后** —— 这是"断言盯系统行为"的前提。

自查:`pytest -q -m "not network"` 仍 16 passed(夹具没人用时不会报错)。

## 3. 任务二 · 三条双端校验用例(约 60 分钟)

**新建** `api_test/testcases/business/test_todos_db.py`。

| # | 用例名 | 操作 | 断言 | 为什么值得写 |
|---|---|---|---|---|
| 1 | `test_created_todo_exists_in_db` | 接口创建 → 直连 DB 查 | 201;库里有这行;`title`/`priority`/`user_id` 与请求一致;`deleted == 0` | **最基本也最重要**:证明"接口说成功"不是空话 |
| 2 | `test_soft_deleted_todo_row_remains_in_db` | 接口删除 → 直连 DB 查 | 接口 204;库里**那行还在**;`deleted == 1`;再走接口查询 → 404 | 区分**软删除**和物理删除 —— 契约明确要求软删除,写错(真删了)会让数据不可恢复 |
| 3 | `test_updated_status_is_persisted`(可选) | 若实现了状态流转接口 | 库里的 `status` 变了 | 有更新接口时才有意义;现在没有,先跳过 |

### ⚠️ 必踩的坑:Session 有缓存,不 `expire_all()` 会读到旧值

实测(先查一次 → 服务端软删除 → 再查):

```
不 expire 再查     : deleted=0     ← 旧值!会造成"软删除没生效"的误判
expire_all() 之后 : deleted=1     ← 真值
```

原因:SQLAlchemy 的 `Session` 有**身份映射缓存**(identity map),同一个主键的对象在同一个 Session 里只查一次;服务端是在**另一个 Session/连接**里改的数据,你这边不会自动刷新。

**规则:每次跨进程(服务端)写完数据后,再查 DB 前先 `db.expire_all()`**。

### 数据清理(否则种子数据会被你污染)

软删除会留下 `deleted=1` 的行,越跑越多。加一个善后夹具:

```python
@pytest.fixture
def created_todos(db):
    """登记本用例创建的 id,结束时【物理删除】,保证种子数据不被污染。"""
    ids: list[int] = []
    yield ids
    for todo_id in ids:
        row = db.query(Todo).filter(Todo.id == todo_id).first()
        if row:
            db.delete(row)
    db.commit()
```

用例里:`def test_xxx(todo_api, db, created_todos):` → 创建后 `created_todos.append(tid)`。

> 为什么这里允许 DB 物理删除?**准备/善后可以用 DB,断言用接口+DB**。这是测开的常规做法(否则你永远清不干净软删除的垃圾行)。

## 4. 任务三 · `inject_api` 夹具 + 故障注入用例(约 45 分钟)

### 4.1 夹具(conftest.py)

```python
@pytest.fixture
def inject_api(server_api, token) -> TodoApi:
    """带故障注入开关的通道:让写接口"返回成功但不写库"。

    开关挂在【连接】上,不进业务方法签名 —— 见 `api/README.md` §7。
    """
    return TodoApi(server_api.with_headers(**{"X-Inject-Bug": "write_fail"}), token)
```

### 4.2 用例(新建 `api_test/testcases/business/test_injection.py`)

| # | 用例名 | 断言 |
|---|---|---|
| 1 | `test_injected_create_returns_201_but_writes_nothing` | 201;响应头 `X-Bug-Injected == "write_fail"`(证明注入确实生效);**DB 里查不到这条** |
| 2 | `test_injected_delete_keeps_row_alive` | 204;`X-Bug-Injected` 回显;**DB 里 `deleted` 仍是 0**(假装删成功) |

**关键断言**:`assert db.query(Todo).filter(Todo.title == title).first() is None`

这条断言就是"双端校验的能力证明":它把"接口撒谎"和"库里的事实"摆在一起对比。

### 4.3 让这条用例"自证有效"(推荐加一条,面试可现场演示)

一条**故意写错**的用例,标 `xfail(strict=True)`,证明"只信接口会漏":

```python
@pytest.mark.xfail(strict=True, reason="单端断言会漏掉静默失败 —— 这正是双端校验存在的理由")
def test_single_end_assertion_is_fooled(inject_api, db):
    title = "xfail-单端会漏"
    r = inject_api.create_todo(title)
    assert r.status_code == 201              # 单端断言:通过
    assert db.query(Todo).filter(Todo.title == title).first() is not None   # 双端断言:必然失败
```

`xfail(strict=True)` 的含义:**它必须失败**。哪天它意外通过了,说明被测系统的注入行为变了 —— 用例会红并提醒你,而不是默默放过。

## 6. 常见坑(全部实测过)

| 坑 | 现象 | 正解 |
|---|---|---|
| **从 `api_test/` 目录跑 pytest** | 双端校验对着空库断言,接口成功但库里永远没数据 | 在**仓库根**跑;`_check_db_target` 夹具会提前报错 |
| **Session 缓存** | 服务端已软删除,你查到 `deleted=0` | 查前 `db.expire_all()` |
| **忘了关 Session** | 连接池耗尽 / 测试进程卡住 | 夹具 `finally: session.close()` |
| **用 `get_db()` 当夹具** | `'generator' object has no attribute 'query'` | 用 `SessionLocal()` |
| **物理删除代替软删除**(在用例里 `db.delete`) | 掩盖了"服务端真的软删了吗"这个问题 | 删数据只能**通过接口**;DB 删除只用于**善后清理** |
| **注入用例只断言 201** | 用例通过,但缺陷完全没被发现 | 必须加"库里查不到"这条双端断言 |
| **`X-Inject-Bug` 没生效**(APP_ENV=prod) | 库里真有数据,用例红 | 确认服务端 `APP_ENV ∈ {dev,test,local}` |
